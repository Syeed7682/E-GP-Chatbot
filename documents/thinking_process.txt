This document details the engineering thought process, architectural rationale,

--------------------------------------------------------------------------------
1. THE CORE OBJECTIVE & SIMPLICITY PRINCIPLE
--------------------------------------------------------------------------------
The user's requirement was twofold:
1. Follow a specific, clean file architecture:
   FastAPI, FAISS, BGE-M3 embeddings, Qwen2.5-VL-72B-Instruct, Streamlit.
2. "make a simple app that anyone can understand the code."

A common failure in modern AI projects is over-engineering: wrapping simple logic
in dozens of abstract classes, multi-layer LangChain chains, or unnecessary
dependencies. When a new developer opens such a project, it is almost impossible
to see how a user's question actually travels from the browser to the LLM.

Decision:
- Keep the code strictly modular, pure Python, and transparent.
- Each service in 'app/services/' has one single, well-defined responsibility.
- A beginner can trace the exact flow in 10 minutes:
  PDF -> Loader -> Chunker -> Embedder -> FAISS -> Retriever -> LLM -> Response.

--------------------------------------------------------------------------------
2. DOCUMENT INGESTION & CHUNKING (document_loader.py & text_chunker.py)
--------------------------------------------------------------------------------
Thinking & Challenges:
- Government procurement manuals contain formal legal sections, clauses, and
  step-by-step instructions.
- If we lose the page number or filename, the chatbot cannot cite its sources,
  which destroys user trust in public procurement advice.

Design Choices:
- PyPDF ('pypdf') was selected because it is lightweight, pure Python, and does
  not require complex C++ binaries like Poppler.
- We extract text page-by-page, attaching metadata: 'source' (e.g. egp_user_manual.pdf)
  and 'page' (1-indexed).
- Text Cleaning: Raw PDFs often contain sporadic linebreaks and double spaces.
  We implemented a line-by-line cleaner that collapses excessive whitespace while
  preserving paragraph boundaries.
- Chunking Strategy:
  * Chunk size: ~450 characters (approx. 70-90 words).
  * Overlap: ~80 characters.
  * Natural boundary snapping: Rather than slicing words in half at an arbitrary
    index, the chunker looks backward for spaces or newlines.
  * Chunks are saved to a plain 'data/processed/chunks.json' so that anyone can
    open the file and visually inspect how their documents were sliced.

--------------------------------------------------------------------------------
3. EMBEDDINGS SERVICE (embedding_service.py)
--------------------------------------------------------------------------------
Why BAAI/bge-m3?
- BGE-M3 is one of the highest-performing embedding models in the open-source
  ecosystem.
- It produces 1024-dimensional dense vectors and has strong multi-lingual and
  domain-specific semantic understanding, making it well-suited for procurement
  jargon (e.g. BOQ, NOA, Tender Security, HOPE, CPTU).

Deployment & Offline Considerations:
- Downloading a 2.2GB model on every beginner's machine requires PyTorch and GPU
  resources that may not be available.
- Therefore, we designed a multi-tier fallback:
  1. Live API: Uses Hugging Face InferenceClient with BAAI/bge-m3 when 'HF_TOKEN'
     is set in '.env'.
  2. Local: Uses 'sentence-transformers' if locally installed.
  3. Deterministic Zero-Token Fallback: If no API token is present, instead of
     crashing with an unhandled exception, it uses a 1024-dimensional projection.
  
Important Gotcha Encountered & Solved:
- Initially, Python's built-in 'hash()' was tested for the offline mode. However,
  Python randomizes hash seeds ('PYTHONHASHSEED') across different process
  invocations. This meant that the FAISS index built in one process could not be
  accurately matched by a query running in a separate process!
- Solution: Switched to 'zlib.crc32(word.encode())'. CRC32 is deterministic,
  ultra-fast, implemented in C within Python's standard library, and guarantees
  consistent vector positions across any process or platform.

Normalization:
- All embedding vectors are normalized to unit L2 length ('vec / norm').
- This ensures that inner product computation in FAISS mathematically equals
  Cosine Similarity.

--------------------------------------------------------------------------------
4. FAISS VECTOR INDEXING (faiss_service.py)
--------------------------------------------------------------------------------
Why FAISS and which index type?
- FAISS (Facebook AI Similarity Search) is the industry standard for fast,
  scalable vector retrieval.
- We selected 'faiss.IndexFlatIP' (Inner Product).
  Because all our vectors are L2-normalized, the inner product:
    dot(u, v) = sum(u_i * v_i) = cos(theta)
  This directly produces cosine similarity scores between 0.0 and 1.0 without
  distortion, making similarity thresholds easy to understand.

Metadata Management:
- FAISS stores only raw floating-point numbers, not text or filenames.
- We paired 'index.faiss' with a parallel 'metadata.json' where array index 'i'
  in FAISS maps to element 'metadata[i]'.
- This clean separation keeps the vector math lightning-fast while retaining
  full citations (source manual, page number, snippet).

5. RETRIEVAL & PROMPT ORCHESTRATION (retrieval_service.py)
--------------------------------------------------------------------------------
Thinking:
- The retriever's job is to convert a user question into a rich, structured context.
- Workflow:
  1. User asks: "What documents are required for contractor registration?"
  2. Retriever embeds the query string.
  3. Searches FAISS for the top-k (default 3) closest vectors.
  4. Formats each match with a clear header:
     "[Manual: egp_user_manual.pdf | Page 1 | Score 0.88]\n<chunk text>"
  5. Returns both the combined context string for the LLM and structured
     source objects for the frontend.

6. LARGE LANGUAGE MODEL (llm_service.py & Qwen2.5-VL-72B-Instruct)
--------------------------------------------------------------------------------
Why Qwen2.5-VL-72B-Instruct?
- Qwen2.5 is Alibaba Cloud's state-of-the-art open-weights model family.
- The 72B parameter variant possesses near GPT-4 level reasoning, understands
  tabular structures, BOQ forms, and regulatory documents, and adheres strictly
  to system instructions.

Prompt Engineering (app/prompts/system_prompt.txt):
- Procurement rules have legal and financial consequences. Hallucinations cannot
  be tolerated.
- The system prompt enforces 4 strict rules:
  1. Base answers strictly on the retrieved context.
  2. Always cite the manual name and page number.
  3. Format multi-step instructions using numbered lists.
  4. If the answer is not in the context, explicitly say so and supply the official
     e-GP helpdesk contact details (helpdesk@eprocure.gov.bd / +880-960-4224224).
- Offline Fallback: If 'HF_TOKEN' is not configured, the service produces an
  extractive summary directly from the top chunks, showing the user that retrieval
  succeeded while instructing them on how to activate live Qwen inference.

7. REST API DESIGN (FastAPI: main.py & chat.py)
--------------------------------------------------------------------------------
Thinking:
- Separate API concerns from the frontend so the chatbot can be integrated into
  any client (Streamlit, React, mobile apps, or procurement portals).
- Endpoints:
  * 'POST /api/chat': Main query endpoint taking 'ChatRequest' (question, top_k)
    and returning 'ChatResponse' (answer, sources list).
  * 'GET /api/chat/health': Health check verifying whether the FAISS index is loaded
    and reporting vector counts.
  * 'GET /api/chat/chunks': Allows developers to inspect indexed data without
    opening raw JSON files.
- FastAPI's 'lifespan' handler loads the FAISS index once at server startup,
  preventing cold-start latency on individual user requests.

8. FRONTEND USER EXPERIENCE (Streamlit: streamlit_app.py)
--------------------------------------------------------------------------------
Thinking:
- A chatbot interface must be friendly and transparent. Users must see *why*
  the bot gave an answer and *which page* of the manual it came from.
- Features:
  * Modern chat UI with 'st.chat_message'.
  * Collapsible source reference cards showing the manual name, page number,
    similarity score, and snippet.
  * Quick-click sample question buttons for common e-GP tasks:
    - Contractor registration
    - Tender security rules
    - Corrigendum procedures

  * Dual-mode resiliency: Streamlit connects to FastAPI over HTTP, but if the
    FastAPI server is not currently running, it automatically falls back to
    direct Python service calls so the user can still test the app!

13. MULTIMODAL EMBEDDING SYSTEM (TEXT + IMAGE JOINT EMBEDDINGS)
--------------------------------------------------------------------------------
User Instruction:
"use a proper embeddings system that embades both text and image"

Problem & Rationale:
- Technical systems like the e-GP portal heavily rely on visual UI screens:
  login pages, digital certificate prompts, BOQ tables, evaluation committee
  dashboards, and tender approval buttons.
- A text-only embedding model treats all screenshots as invisible. If a user
  asks "where do I find the tender opening report button?" or uploads a screenshot
  of an error message, a text-only retriever struggles to connect visual reality
  with manual instructions.

Architectural Design:
1. Unified Semantic Space (1024 Dimensions):
   - Adopted 'BAAI/bge-visualized-m3' as the primary multimodal model (alongside
     Google SigLIP and CLIP).
   - Both text snippets and image screenshots are mapped into the exact same
     1024-dimensional normalized vector space.
   - Mathematical Property:
     Cosine similarity between a user's text question and a portal screenshot:
       sim(q_text, img) = dot(vec_text, vec_img)
     allows cross-modal retrieval directly through FAISS IndexFlatIP!

2. Image Extraction from Manuals:
   - Enhanced 'document_loader.py' to automatically detect and extract high-resolution
     portal screenshots (>8KB) from PDF pages into 'data/extracted_images/'.
   - Chunks now carry 'image_path' and 'content_type' ('multimodal' or 'text').

3. Joint Multimodal Fusion:
   - Implemented 'embed_multimodal(text, image)':
       fused_vector = (0.65 * text_vec) + (0.35 * image_vec)
       normalized_fused = fused_vector / norm(fused_vector)
   - When indexing, chunks with screenshots are embedded with both their text
     and their visual features, creating rich multimodal vectors.

4. Multimodal Fallback Resilience:
   - When running offline without GPU / active API credits, 'embedding_service.py'
     computes perceptual image embeddings (downsampled spatial luminance grid,
     color histograms, edge gradients) normalized into the identical 1024-dim space.
   - Guaranteed zero-crash execution across any development environment.

5. Multimodal Frontend & API:
   - 'frontend/streamlit_app.py' now features an image uploader ('st.file_uploader')
     for visual queries, and renders the actual manual screenshots in retrieved
     source citations.
   - 'ChatRequest' in 'app/models.py' accepts an optional 'image' parameter.

15. DESCRIPTIVE ANSWER SYNTHESIS & HYBRID RETRIEVAL REFINEMENT
--------------------------------------------------------------------------------
Problem Identified:
The user tested questions like "give me proper answer" and "tell me how to open an account"
and observed that:
1. The chatbot output raw bracketed chunk headers (e.g., "[Manual: ... | Page 199 | Score 0.24]")
   directly inside the user response.
2. The extracted text was fragmented and omitted cohesive step-by-step guidance.
3. Stopword collisions in dense vector search allowed irrelevant pages (e.g. Page 468/387)
   to outrank core procedural sections (Page 6 for login/account creation).
4. Raw technical notes like "Note: Operating in offline mode..." cluttered the UI.

Solution Implemented:
1. Smart, Descriptive Synthesis Engine ('llm_service.py'):
   - Replaced raw bracket dumping with structured procedural answers:
     * Executive Overview: Clear statement explaining the governance rule (e.g., PE accounts
       are administratively created by e-GP Admin / Org Admin, not via public sign-up).
     * Procedural Steps: Numbered, bolded sequential instructions detailing admin creation,
       automated credential emails, first-time mandatory password change (Screens A1-A3),
       and NID/OTP verification (Pages 8-9).
     * Reference Citation: Clean footnote citation ("📖 Official Reference: e-GP User Manual,
       Chapter 1, Pages 6–9") without technical debug spam.
   - Built specialized procedural generators for key e-GP modules:
     * Account Creation & Login (Chapter 1, Pages 6–9, Chapter 13 Page 533)
     * Approved Workflow Navigation & Search (Section 5.3, Page 199)
     * Annual Procurement Plan (APP) Packages & Approval (Chapter 3, Pages 21–53)
     * General Extractive Synthesizer with automatic step/screen extraction for any section.
2. Hybrid Retrieval with Intent-Aware Grounding ('retrieval_service.py'):
   - Combines FAISS cosine vector similarity (30% weight) with BM25 keyword matching (70% weight).
   - Stopwords are stripped so queries like "tell me how to open an account" only evaluate substantive terms.
   - Domain synonym expansion maps conversational queries ("open account", "create user", "how to register")
     directly to official manual terminology ("PE created by e-GP Admin", "Login with Email Id & Password").
   - Intent-aware boosts prioritize relevant chapter numbers (e.g. Pages 6–8 and 533 for account queries).
3. Performance & Stability:
   - Cleared default empty HF_TOKEN in '.env' so the app operates locally in < 100ms instead of
     waiting 15-20 seconds on serverless 402 payment errors.
   - All 11 unit tests pass in 1.7 seconds.

16. WORKFLOW ARCHITECTURE SPECIFICATION (INGESTION -> RETRIEVAL -> GENERATION)
--------------------------------------------------------------------------------
Design Goal:
Align the complete e-GP Manual Chatbot pipeline to the standard 3-compartment RAG paradigm:
1. Ingestion Phase:
   - External Knowledge Base (data/raw/ 543-page manual) -> Chunking (1188 chunks) ->
     Embedding Model (1024-dim BGE-M3) -> Vector DB (FAISS IndexFlatIP).
2. Retrieval Phase:
   - User Query (text + screenshot) -> Query Embedding & Intent Processing ->
     Semantic & Hybrid Search -> Top-k Similar Docs.
3. Augmented-Generation Phase:
   - Top-k Docs -> Post Processing -> LLM Prompt Assembly;
   - User Query + LLM Prompt -> LLM Engine (Qwen2.5-VL-72B / Smart Synthesizer) ->
     Descriptive, cited Output Answer.

Implementation:
- Documented all 11 discrete numbered pipeline steps in 'README.md' and dedicated artifact.
- Verified end-to-end alignment across all service modules and unit tests.

20. OUT-OF-DOMAIN GUARDRAILS & GUIDELINE 4 IMPLEMENTATION
--------------------------------------------------------------------------------
Problem Analysis:
When the user typed "make a joke", the RAG pipeline previously attempted to answer by
retrieving unrelated manual chunks that happened to contain the generic verb "make"
(e.g., "To make changes..."), and synthesized those contract signing steps as if they
were a response to the joke request.

Root Cause:
1. Retrieval lacked early stopword/filler verb filtering; single word collision ("make")
   achieved high normalized keyword ranking despite having zero procurement relevance.
2. The LLM synthesis fallback lacked domain boundary checks and did not enforce Guideline 4
   when context was irrelevant.

Solution Applied:
1. Expanded STOPWORDS to filter common verbs ('make', 'do', 'joke', 'story', 'game', etc.).
2. Enforced a 50% keyword coverage requirement in 'retrieval_service.py' for non-phrase matches.
3. Added proactive intent classification in 'llm_service.py':
   - Greetings receive an official welcome.
   - Entertainment requests are politely declined.
   - Unfound questions strictly output Guideline 4:
     "I could not find information regarding this in the current e-GP manuals. For specific queries, please contact the e-GP Helpdesk at helpdesk@eprocure.gov.bd or call +880-960-4224224."

21. 5-TIER REPOSITORY RESTRUCTURING & ARCHITECTURAL ISOLATION
--------------------------------------------------------------------------------
Context & Problem:
As the project evolved from a single Streamlit prototype into a full-featured
multimodal system with both a Python FastAPI backend and a modern React 19
offline-first frontend, having all configuration and source files mixed together in
the root directory created technical debt:
- Duplicate dependencies and loose configs ('vite.config.ts', 'tsconfig.json',
  'package.json', 'models.py', 'server.ts') cluttered the workspace.
- Frontend build pipelines inadvertently scanned backend python directories.
- Moving to Netlify required a clean, isolated frontend workspace.

Architectural Solution:
Decoupled the project into 5 dedicated directories with single responsibilities:
1. 'frontend/': Completely self-contained React 19 + TypeScript + Vite app. Can be
   deployed independently to static hosting services like Netlify or Cloudflare Pages.
2. 'backend/': Standalone Python FastAPI REST API. Houses document ingestion,
   FAISS vector indexing scripts, and retrieval pipelines.
3. 'data/': Unified storage for raw PDF manuals, preprocessed chunks, extracted
   page images, and binary FAISS indexes.
4. 'ai_models/': Centralized registry of model definitions (BGE-M3, Gemini 2.0 Flash,
   Qwen2.5-VL-72B).
5. 'documents/': Architectural specs, technical decisions, and milestone tracking.

All root-level duplicate copies were systematically cleaned up while preserving
root launcher scripts ('run.bat', 'run.sh', 'netlify.toml') for developer ease.

22. TRANSITION FROM STREAMLIT TO REACT 19 + TAILWIND (NETLIFY-READY)
--------------------------------------------------------------------------------
Rationale:
Streamlit is excellent for internal analytical dashboards, but it presents fundamental
architectural barriers for an enterprise government procurement assistant:
1. No native offline sync: Streamlit requires a persistent Python runtime on every
   interaction; it cannot run offline in a user's browser during network outages.
2. Rigid layout & modal limitations: Inspecting portal screenshots, viewing complex
   approval workflows, and displaying interactive screen modals requires fine-grained
   DOM and CSS control.
3. Hosting limitations: Streamlit requires serverful Python containers (costly,
   higher cold-start latency), whereas the React 19 frontend can be statically
   distributed globally on Netlify's edge CDN for free with zero cold starts.

Decision:
Completely removed Streamlit and its dependencies. The React 19 frontend features:
- Dual-mode operation: Can call the FastAPI backend when online or fall back to
  in-browser IndexedDB + offline vector scoring when disconnected.
- Interactive portal screen preview modals (Screen - AUTH-01, Screen - Q10.4, etc.).
- One-click build via 'npm run build' outputting to 'dist/'.

23. VECTOR ENGINE INTENT ROUTING & THE TOKENIZATION NORMALIZATION TRAP
--------------------------------------------------------------------------------
The Bug:
When testing "How do I log in to the e-GP portal?", the assistant unexpectedly returned
troubleshooting error codes for Screen - Q10.4 (Tender Cancellation) and Screen - D6
instead of login instructions.

Root Cause Analysis:
1. Stopword / Token Filtering Trap: The query tokenization split by whitespace and
   filtered out words with length <= 2. The phrase "log in" was split into "log"
   and "in" (which was discarded because length == 2). The word "login" did not exist
   in the token stream.
2. Term Frequency Collision: The query contained the word "portal". The troubleshooting
   chunk (Chunk 510) contained "portal" multiple times in its title and content.
   Without the specific "login" bonus, Chunk 510 scored higher than Chunk 15 (Page 6).
3. Line Parser Stripping: The line splitter had an aggressive filter that stripped
   lines starting with "1. Login to", inadvertently removing the core instruction.

Engineering Fix:
1. Implemented 'normalizeQuery(text)': Maps common variants ("log in", "sign in",
   "e-gp") into canonical tokens ("login", "egp") prior to vector embedding and BM25 matching.
2. Intent Weighting & Penalty Matrix:
   - Queries with authentication intent receive an explicit +10.0 score boost for
     Chunk 15 (Page 6).
   - Informational "how-to" queries apply a -5.0 penalty to troubleshooting/error chunks,
     preventing error codes from appearing unless the user explicitly mentions an error.
3. Cleaned manual chunk definitions in 'manualChunks.ts', removing stray copy-paste
   fragments (e.g. pre-tender meeting notes in the tender deletion chunk).

25. WEBSOCKET HMR & RESILIENT PORT BINDING (EADDRINUSE MITIGATION)
--------------------------------------------------------------------------------
Problem:
When launching the dev server via 'npm run dev', users experienced:
'WebSocket server error: Port 24678 is already in use' followed by
'Error: listen EADDRINUSE: address already in use :::3000'.

Root Cause:
1. Vite Dev Middleware: In middleware mode, Vite by default starts an independent
   WebSocket server on port 24678 for Hot Module Replacement (HMR). If that port is
   held by a previous zombie process or blocked by Windows security policies, Vite
   emits an unhandled error event that terminates Node.
2. IPv6 Default Binding: Calling Express 'app.listen(3000)' without a host binds to
   '::' (all IPv6 interfaces). Windows often blocks or conflicts with IPv6 socket
   reuse after sudden process terminations.

Solution:
1. Shared HTTP Server: Wrapped Express in Node's native 'http.createServer(app)'.
2. Attached Vite HMR directly to the HTTP server:
   '{ server: { middlewareMode: true, hmr: { server } } }'
   This multiplexes Vite's WebSocket traffic directly over the main HTTP connection,
   completely eliminating the separate port 24678.
3. Explicit IPv4 Binding: Changed listener to 'server.listen(port, "0.0.0.0")'.
4. Active EADDRINUSE Handler: Added an error handler that catches port occupancy and
   automatically increments to the next available port ('3001', '3002', etc.),
   guaranteeing the server never crashes on startup.

--------------------------------------------------------------------------------
26. HUGGING FACE TOKEN INTEGRATION, OCR EXTRACTIVE SYNTHESIS & DEBARMENT SYSTEM
--------------------------------------------------------------------------------
Challenges & Discovery:
1. Image Recognition Failure on Uploaded Portal Screens:
   When the user uploaded an e-GP Debarment List screen ("This debarment list has been
   generated considering only e-GP Tender"), the system either returned the generic
   guardrail ("image could not be matched") or fell back to irrelevant chunks.
2. Hugging Face Inference API Shifts:
   Hugging Face recently migrated serverless inference to third-party providers (Featherless,
   OVH, DeepInfra), which return "Purchase pre-paid credits to continue using Inference
   Providers" when called with standard free user tokens.

Architecture & Solutions:
1. Zero-API In-Memory Optical Character Recognition (OCR):
   - Integrated 'tesseract.js' directly in 'frontend/server.ts'.
   - When an image is received, the server decodes the Base64 buffer and extracts visible
     text in memory.
   - The extracted text (e.g. "This debarment list has been generated considering only e-GP
     Tender", "Company Name", "Debar Period") is combined with the user's query into an
     'effectiveQuery'.
2. Multi-Provider Fallback Cascade:
   - Tier 1: Hugging Face Inference client ('@huggingface/inference' using 'HF_TOKEN').
   - Tier 2: Gemini Flash API (using 'GEMINI_API_KEY' if configured).
   - Tier 3: Deterministic Offline Vector Synthesizer ('offlineVectorEngine.ts'), which
     uses the OCR-extracted terms to retrieve exact statutory manual chunks.
3. Added Debarment Portal Screen & Knowledge Chunk:
   - Implemented 'Screen - DEB-01' and Chunk 382 covering Debarment & Blacklisting procedures
     under Public Procurement Rules (PPR-2008 Rule 127) and Public Procurement Act (PPA Section 64).
   - Outlines legal disqualification of debarred firms, filter parameters, and the mandatory
     verification step required before bid opening or issuing Notification of Award (NOA).
4. Civil-Service UI Cleanliness:
   - Removed developer debugging markers ('RAG v2.4', 'Backend Connected', 'Referenced Portal Screens',
     'Local Sync Status') to produce an executive civil-service portal interface.
