# Implementation Thinking Process

## Context & Goals
The e‑GP Manual Assistant must provide **accurate, grounded answers** to user queries about the Bangladesh e‑GP Procuring Entity User Manual. Key requirements include:
1. Full‑text semantic retrieval over a 543‑page manual.
2. Domain‑specific keyword weighting for procurement terminology.
3. Multimodal support – ability to process screenshots (OCR + vision model).
4. Robust fallback paths when hosted model providers are unavailable.
5. A clean, production‑ready deployment model (FastAPI backend + Vite/React frontend).

## Major Design Decisions
| Decision | Rationale |
|----------|-----------|
| **Hybrid Retrieval (FAISS + BM25)** | FAISS provides dense semantic similarity using BGE‑M3 embeddings, while BM25 captures exact keyword matches for procurement‑specific terms. Combining them (0.7 × dense + 0.3 × BM25) yields higher recall for procedural queries. |
| **Local Qwen 2.5‑VL‑3B‑Instruct** as primary LLM | Offers both text and vision capabilities on a single model, simplifying the image‑auto‑shift workflow. GPU availability is optional – we fall back to Groq hosted models. |
| **Vision Auto‑Shift** | When an image is attached, the backend runs Tesseract OCR to extract any portal text, then forces the vision model regardless of the UI toggle. This ensures screenshots are interpreted correctly and prevents hallucinations on off‑topic images. |
| **Offline Synthesis Path** | Guarantees a deterministic answer even when all external providers fail (e.g., rate‑limit or 402 errors). The synth‑routine formats responses with clear citations and procedural headings. |
| **CORS‑Driven Frontend/Backend Separation** | The frontend is a static Netlify site; only the backend holds secrets. Explicit `CORS_ORIGINS` in `.env` locks down which origins may call the API. |
| **Docker‑Ready Backend** | All runtime configuration lives in environment variables; the code loads the FAISS index on startup, making containerisation trivial. |
| **Documentation‑First** | Updated README, API docs, deployment guide, architecture diagram, and project plan to keep future contributors aligned. |

## Step‑by‑Step Engineering Flow
1. **Data Ingestion**
   - PDF loaded via `document_loader.py` → clean text → chunked with overlap (≈500 words).
   - Each chunk stored with `page`, `chunk_id`, and `source` metadata.
2. **Embedding Generation**
   - BGE‑M3 (1024‑dim) produces dense vectors for each chunk.
   - Optional image embeddings using CLIP/SigLIP for screenshots (future extension).
3. **FAISS Index Construction**
   - `IndexFlatIP` built, vectors normalized for cosine similarity.
   - Metadata persisted in `data/faiss_index/metadata.json` for citation mapping.
4. **Retrieval Service**
   - Query preprocessing: stop‑word removal, domain synonym expansion (e.g., "open account" → login terms).
   - Dense search → top‑k IDs & scores.
   - BM25 search → parallel top‑k IDs & scores.
   - Linear fusion → final ranking; filter out TOC/pages ≤ 5.
5. **Vision Handling**
   - If `image_base64` present, run Tesseract OCR in‑memory.
   - Append OCR text to query before retrieval.
   - Force vision model (`Qwen2.5‑VL‑3B‑Instruct`) via `use_alt_model` flag or auto‑shift.
6. **LLM Service**
   - Build prompt: system instructions + formatted context (+ citations).
   - Preference order: Local model → Groq → Gemini → Offline synthesis.
   - Post‑process answer: ensure citations, remove debug artefacts, format procedural steps.
7. **API Layer**
   - `POST /api/chat` orchestrates OCR, retrieval, LLM call, and source packaging.
   - Health endpoints expose index readiness and model configuration.
   - Manual endpoints serve PDF pages and extracted images.
8. **Frontend Integration**
   - Vite/React UI sends `ChatRequest` objects.
   - Displays answer, source list, and clickable page images.
   - E1/E2 toggle sets `use_alt_model` flag in the request.
9. **Testing & Validation**
   - Unit tests for chunking, embedding dims, FAISS search correctness.
   - Integration tests for chat flow, error handling, and fallback paths.
   - All 10 tests pass locally (`pytest -q`).
10. **Deployment**
    - Backend containerisation: `uvicorn app.main:app` with environment‑driven config.
    - Netlify static build: `npm run build` publishes `dist/`.
    - CORS and secrets kept server‑side only.

## Risks Identified & Mitigations
- **GPU Unavailability** – `USE_LOCAL_LLM` flag disables local Qwen; system falls back to Groq without code changes.
- **Provider Rate Limits** – Implement exponential back‑off in `llm_service._call_groq_api`; monitor 429 responses.
- **Manual Updates** – Re‑run ingestion scripts; CI pipeline can automate index rebuild on PDF version bump.
- **Security** – All tokens stored in backend `.env`; frontend only receives `VITE_API_BASE_URL`.
- **Off‑topic Images** – OCR + domain validators reject non‑portal screenshots, returning a polite error message.
